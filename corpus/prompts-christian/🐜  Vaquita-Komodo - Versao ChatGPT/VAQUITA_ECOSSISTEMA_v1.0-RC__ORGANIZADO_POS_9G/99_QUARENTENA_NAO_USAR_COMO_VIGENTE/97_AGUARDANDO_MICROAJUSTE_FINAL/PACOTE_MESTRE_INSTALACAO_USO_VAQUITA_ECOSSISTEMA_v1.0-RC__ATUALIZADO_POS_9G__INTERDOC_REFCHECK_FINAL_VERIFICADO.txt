## 0. COMO USAR ESTE PACOTE

Este arquivo é o guia de entrada do Ecossistema Vaquita v1.0-RC.

Use este pacote quando quiser:

1. iniciar uma revisão acadêmica com a Vaquita;
2. saber quais arquivos carregar em cada chat;
3. decidir quando usar Komodo, BVAA, Jararaca ou Handoff;
4. migrar revisão para novo chat;
5. evitar confusão entre módulos;
6. preservar o estado do projeto sem depender da memória do chat anterior.

Este pacote não substitui os prompts operacionais dos módulos.

Ele diz qual arquivo usar, em qual chat, em qual ordem e com qual finalidade.

## 3. FLUXO DE INSTALAÇÃO RÁPIDA — REVISÃO COM VAQUITA

### Passo 1 — Abrir chat da Vaquita

Abra um novo chat.

Esse chat será o chat principal de revisão.

Nome mental do chat:

CHAT VAQUITA

---

### Passo 2 — Carregar arquivo principal da Vaquita

Anexe ou cole:

VAQUITA_ORQUESTRADOR_v1.0-RC__PROMPT_OPERACIONAL_CONSOLIDADO_AUDITADO.txt

---

### Passo 3 — Colar bootstrap da Vaquita

Depois de carregar o arquivo principal, cole:

BOOTSTRAP_CARREGAMENTO_VAQUITA_v1.0-RC.txt

Aguarde a resposta de boot.

---

### Passo 4 — Enviar BLOCO 0

Cole o BLOCO 0 do projeto.

Use BLOCO 0 quando o projeto já estiver minimamente definido.

Use BLOCO 0 AVANÇADO quando houver:

1. tese ou dissertação longa;
2. múltiplos capítulos;
3. bibliografia extensa;
4. mapas estruturais;
5. regras específicas de estilo;
6. necessidade de alta blindagem anti-deriva.

---

### Passo 5 — Executar COMANDO 0

Depois do BLOCO 0, envie:

COMANDO 0

A Vaquita deve reconstruir:

1. tipo de texto;
2. perfil temático;
3. capítulo;
4. seção;
5. unidade de revisão;
6. padrão de citação;
7. regras de estilo;
8. estado inicial;
9. pendências;
10. riscos de deriva.

---

### Passo 6 — Executar COMANDO 1

Depois da reconstrução do estado, envie:

COMANDO 1

A Vaquita inicia a revisão do primeiro trecho/parágrafo.

---

### Passo 7 — Avançar com PROXIMO / PRÓXIMO

Depois de cada entrega, para continuar, envie:

PROXIMO

ou

PRÓXIMO

A Vaquita deve avançar preservando ESTADO_VAQUITA.

Atenção:

Se houver bloqueio operacional, como CORRIGIR_ANTES_DE_AVANÇAR emitido pelo Komodo, PROXIMO permanece bloqueado até correção ou comando humano adequado.

## 4. QUANDO ACIONAR CADA AUXILIAR

### Orientação pós-FASE 9.G — roteamento múltiplo simultâneo

Quando houver simultaneamente risco textual, documental e estrutural, a Vaquita pode gerar PACOTE_KOMODO, PACOTE_BVAA e PACOTE_JARARACA separadamente.

Os retornos devem ser integrados sem mistura de funções:

1. Komodo preserva bloqueio textual, quando houver;
2. BVAA preserva pendência documental, quando houver;
3. Jararaca preserva ressalva estrutural, quando houver.

A integração simultânea não autoriza correção automática, liberação bibliográfica, fusão, corte, realocação ou avanço para PROXIMO.

---

### 4.1. Acionar Komodo

Use Komodo quando houver dúvida sobre:

1. fidelidade entre original e revisado;
2. perda de densidade;
3. apagamento de nuance;
4. voz autoral;
5. condensação arriscada;
6. risco de a revisão ter mudado o argumento;
7. caso em que a revisão ficou mais clara, mas pode ter perdido função argumentativa.

A Vaquita deve gerar:

PACOTE_KOMODO

Depois, no chat Komodo, cole o pacote.

O Komodo devolve:

RETORNO_KOMODO

Volte para a Vaquita e integre com:

INTEGRAR_RETORNO_KOMODO

Vereditos possíveis:

APROVADO

APROVADO_COM_RESSALVAS

CORRIGIR_ANTES_DE_AVANÇAR

BLOQUEAR_AVANÇO

Regra pós-FASE 9.E:

Quando o Komodo devolver CORRIGIR_ANTES_DE_AVANÇAR, esse veredito deve ser tratado como bloqueio operacional, não como ressalva simples.

Isso significa:

1. a versão revisada não deve ser consolidada;
2. a ação no manuscrito deve permanecer não consolidada, quando aplicável;
3. PROXIMO deve ficar bloqueado até correção;
4. a Vaquita deve corrigir ou aguardar comando humano para ajuste;
5. Handoff deve preservar o bloqueio se houver migração;
6. o retorno do Komodo não deve ser reduzido a recomendação genérica.

O Komodo não deve:

1. revisar no lugar da Vaquita;
2. criar versão final substitutiva;
3. acionar BVAA;
4. acionar Jararaca;
5. acionar Handoff;
6. aplicar ação no manuscrito.

---

### 4.2. Acionar BVAA

Use BVAA quando houver dúvida sobre:

1. página;
2. citação literal;
3. referência;
4. fonte;
5. pertinência documental;
6. uso seguro de bibliografia;
7. risco de inventar página, DOI, edição ou trecho.

A Vaquita deve gerar:

PACOTE_BVAA

Depois, no chat BVAA, cole o pacote.

O BVAA devolve:

RETORNO_BVAA

Volte para a Vaquita e integre com:

INTEGRAR_RETORNO_BVAA

Regra crítica:

PENDENTE_BVAA nunca vira LIBERADA sem nova evidência verificável.

Fluxo integrado BVAA + Handoff validado:

A FASE 9.F aprovou a cadeia Vaquita + BVAA + Handoff. PENDENTE_BVAA permanece pendência documental ativa e PEDIR_PDF permanece exigência documental, não autorização de uso com ressalva.

---

### 4.3. Acionar Jararaca

Use Jararaca quando houver dúvida sobre:

1. redundância;
2. repetição;
3. retomada funcional;
4. sobreposição entre seções;
5. progressão argumentativa;
6. deriva estrutural;
7. necessidade de corte, fusão, realocação ou condensação.

A Vaquita deve gerar:

PACOTE_JARARACA

Depois, no chat Jararaca, cole o pacote.

A Jararaca devolve:

RETORNO_JARARACA

Volte para a Vaquita e integre com:

INTEGRAR_RETORNO_JARARACA

Regra crítica:

Corte, fusão, realocação e reorganização sensível exigem confirmação humana.

Fluxo integrado já validado:

FASE 9.C — Vaquita + Jararaca + Handoff aprovada.

---

### 4.4. Acionar Handoff

Use Handoff quando houver necessidade de:

1. migrar para novo chat;
2. preservar ESTADO_VAQUITA;
3. transferir revisão em andamento;
4. preservar retornos auxiliares;
5. registrar testes, falhas, emendas e retestes;
6. criar pacote de migração;
7. criar pacote condicional;
8. evitar resumo destrutivo.

A Vaquita ou o usuário deve gerar:

PACOTE_HANDOFF

Depois, no chat Handoff, cole o pacote.

O Handoff pode devolver:

RETORNO_HANDOFF

ou

PACOTE_HANDOFF_VAQUITA

ou

PACOTE_DE_MIGRACAO

ou outro pacote de handoff apropriado.

Para retomar em novo chat Vaquita, use:

RETOMAR_VAQUITA_COM_HANDOFF

Regra pós-R4.3 e pós-FASE 9.E:

Quando houver contexto suficiente e finalidade operacional de migração Vaquita, o Handoff consolidado deve gerar PACOTE_HANDOFF_VAQUITA diretamente.

Quando o PACOTE_HANDOFF contiver RETORNO_KOMODO integrado com CORRIGIR_ANTES_DE_AVANÇAR, o Handoff deve preservar esse estado como bloqueio operacional.

O Handoff deve preservar:

1. RETORNO_KOMODO integrado;
2. VEREDITO_KOMODO: CORRIGIR_ANTES_DE_AVANÇAR;
3. status operacional BLOQUEADO PARA AVANÇO, quando informado;
4. ação no manuscrito como não consolidada;
5. PROXIMO bloqueado até correção;
6. pontos específicos indicados pelo Komodo para ajuste futuro;
7. ausência ou presença de pendências BVAA/Jararaca conforme o pacote.

O Handoff não deve:

1. corrigir o trecho;
2. gerar nova versão revisada;
3. transformar CORRIGIR_ANTES_DE_AVANÇAR em APROVADO_COM_RESSALVAS;
4. aplicar ação no manuscrito;
5. reacionar Komodo;
6. criar pendência BVAA inexistente;
7. acionar Jararaca sem motivo estrutural;
8. avançar fase ou parágrafo.

Regra pós-FASE 9.G:

Se PACOTE_HANDOFF contiver simultaneamente RETORNO_KOMODO, RETORNO_BVAA e RETORNO_JARARACA integrados, o Handoff deve gerar PACOTE_HANDOFF_VAQUITA preservando o estado integrado, sem revisar texto, sem verificar fonte, sem auditar estrutura e sem resolver pendências.

O Handoff deve preservar separadamente:

1. bloqueio textual do Komodo;
2. pendência documental do BVAA;
3. ressalva estrutural da Jararaca;
4. PROXIMO bloqueado quando houver pendência bloqueante;
5. ações anteriores já consolidadas.

O Handoff não deve transformar estado integrado em autorização automática de correção, liberação bibliográfica, fusão, corte, realocação ou avanço.

4. a revisão precisa ser retomada em novo chat;
5. o usuário quer preservar estado antes de pausa;

## 7. REGRA DE PRIMEIRA RESPOSTA EM NOVO CHAT

Quando um novo chat receber pacote de migração ou retomada, a primeira resposta deve:

1. reconhecer o pacote;
2. reconstruir o estado;
3. listar decisões consolidadas;
4. listar decisões abertas;
5. listar pendências;
6. listar separadamente bloqueio textual, pendência documental e ressalva estrutural, quando existirem;
7. listar riscos;
8. indicar próximo passo;
9. aguardar confirmação ou comando.

A primeira resposta não deve:

1. revisar texto acadêmico;
2. avançar parágrafo;
3. avançar seção;
4. resolver pendência;
5. gerar novo pacote auxiliar sem comando;
6. apagar falha corrigida;
7. resumir destrutivamente;
8. transformar pendência em decisão consolidada.

## 9. REGRAS ANTI-DERIVA

Regra 1:

Não resumir destrutivamente.

Regra 2:

Não apagar nomes técnicos, comandos, arquivos, versões, testes, falhas ou emendas.

Regra 3:

Não transformar pendência em decisão.

Regra 4:

Não transformar falha corrigida em falha ativa.

Regra 5:

Não apagar falha corrigida do histórico técnico.

Regra 6:

Não misturar núcleo universal com caso específico.

Regra 7:

Não declarar criado arquivo que não foi efetivamente criado.

Regra 8:

Não declarar fonte verificada sem BVAA.

Regra 9:

Não inventar página, referência, DOI ou citação literal.

Regra 10:

Não avançar fase sem confirmação humana.

Regra 11:

Quando um RETORNO_KOMODO trouxer CORRIGIR_ANTES_DE_AVANÇAR, esse veredito deve ser tratado como bloqueio.

O sistema deve:

1. preservar o retorno;
2. registrar a ação no manuscrito como não consolidada, quando aplicável;
3. manter PROXIMO bloqueado até correção;
4. impedir avanço automático;
5. aguardar comando humano ou correção pela Vaquita;
6. preservar os pontos concretos indicados pelo Komodo.

O sistema não deve:

1. suavizar o bloqueio;
2. tratar o trecho como aprovado;
3. converter o veredito em ressalva simples;
4. apagar os alertas;
5. resumir o retorno de modo destrutivo;
6. corrigir automaticamente durante handoff ou retomada.

## 10. CHECKPOINT RÁPIDO ANTI-DERIVA

Use quando:

1. mudar microfase;
2. concluir teste;
3. iniciar novo auxiliar;
4. incorporar emenda;
5. escolher próxima frente;
6. houver risco moderado.

Modelo:

CHECKPOINT RÁPIDO ANTI-DERIVA

Antes de continuar, verifique:
1. Em que fase estamos?
2. Quais decisões já foram consolidadas?
3. Quais decisões ainda estão abertas?
4. Há risco de deriva, contradição ou esquecimento?
5. Qual é o próximo passo correto?

Não entregue versão final de prompt.
Não avance de fase sem confirmar.
Não resuma destrutivamente.

---

## 11. PROTOCOLO ANTI-DERIVA COMPLETO

Use quando:

1. houver pausa longa;
2. houver migração de chat;
3. for montar versão final de prompt;
4. houver risco alto;
5. houver muitas decisões abertas;
6. usuário solicitar protocolo completo.

O protocolo completo deve reconstruir:

1. estado do projeto;
2. fases concluídas;
3. fase atual;
4. produtos criados;
5. decisões consolidadas;
6. decisões abertas;
7. testes executados;
8. falhas e emendas;
9. arquivos principais;
10. riscos;
11. próximo passo correto.

3. inventar página;
