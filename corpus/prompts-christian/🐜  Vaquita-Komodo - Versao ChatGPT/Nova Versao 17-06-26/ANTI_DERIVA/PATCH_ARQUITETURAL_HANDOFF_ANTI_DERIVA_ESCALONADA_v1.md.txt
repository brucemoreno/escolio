### 8.6. Inserção na seção de gate de saída

INSERIR:

GATE_ANTI_DERIVA_HANDOFF:
Antes de gerar pacote final, o Handoff deve classificar o tipo de saída:

1. PACOTE_HANDOFF_PREVENTIVO;
2. PACOTE_HANDOFF_VAQUITA;
3. PACOTE_HANDOFF_CONDICIONAL;
4. RETORNO_HANDOFF;
5. MIGRAÇÃO_BLOQUEADA_POR_ESTADO_INSUFICIENTE.

Critérios:

PACOTE_HANDOFF_PREVENTIVO:
usar quando a função for preservar estado antes de saturação, continuidade excessiva, risco médio/alto controlável ou limite preventivo atingido.

PACOTE_HANDOFF_VAQUITA:
usar quando houver fim de capítulo, mudança de capítulo, risco crítico, perda de estado confiável ou condição de handoff obrigatório.

PACOTE_HANDOFF_CONDICIONAL:
usar quando houver estado parcialmente suficiente, mas com lacunas que precisam ser explicitamente confirmadas no chat de destino.

RETORNO_HANDOFF:
usar quando o usuário pediu avaliação do pacote, auditoria de completude ou diagnóstico do handoff, e não geração de pacote operacional.

MIGRAÇÃO_BLOQUEADA_POR_ESTADO_INSUFICIENTE:
usar quando os campos mínimos necessários para continuidade segura estiverem ausentes e não houver base para reconstruí-los.

## 9. Regras de preservação de ANTI_DERIVA_ESCALONADA

REGRA 1:
Se o pacote de origem contiver ANTI_DERIVA_ESCALONADA, o Handoff deve preservar esse bloco com o mesmo nome.

REGRA 2:
O Handoff não deve criar nome paralelo desnecessário para ANTI_DERIVA_ESCALONADA.

REGRA 3:
O Handoff não deve substituir ANTI_DERIVA_ESCALONADA por:

1. “estado anti-deriva preservado”;
2. “contadores mantidos”;
3. “protocolo preservado”;
4. “risco controlado”;
5. “continuidade segura”.

Essas formulações podem aparecer como comentários, mas não substituem o bloco material.

REGRA 4:
Quando algum campo de ANTI_DERIVA_ESCALONADA estiver ausente no pacote de origem, o Handoff deve marcar:

CAMPO AUSENTE NO PACOTE DE ORIGEM:
[...]

Não deve inventar valor.

REGRA 5:
Quando um campo estiver “a confirmar”, o Handoff deve preservar “a confirmar”.

REGRA 6:
Quando a política ativa for personalizada, o Handoff deve preservar os limiares exatos.

REGRA 7:
Quando a política ativa for conservadora, moderada, leve ou crítica, o Handoff deve preservar a nomenclatura e os limiares recebidos.

REGRA 8:
O Handoff não deve recalcular política anti-deriva sem solicitação explícita.

REGRA 9:
O Handoff não deve relaxar política crítica para conservadora, moderada ou leve.

REGRA 10:
O Handoff não deve converter política “a confirmar” em política consolidada.

## 12. Distinção entre PACOTE_HANDOFF_PREVENTIVO e PACOTE_HANDOFF_VAQUITA

### 12.1. PACOTE_HANDOFF_PREVENTIVO

DEFINIÇÃO:
Pacote de preservação preventiva de estado antes de saturação, continuidade excessiva ou risco operacional crescente.

USAR QUANDO:

1. limite preventivo for atingido;
2. houver risco médio/alto controlável;
3. houver longa continuidade no mesmo chat;
4. houver necessidade de preservar estado antes de perda de confiabilidade;
5. a etapa ainda estiver em andamento.

NÃO SIGNIFICA:

1. etapa concluída;
2. capítulo concluído;
3. seção concluída;
4. pendências resolvidas;
5. retorno auxiliar integrado;
6. PROXIMO liberado.

FORMULAÇÃO OBRIGATÓRIA:
Este é um PACOTE_HANDOFF_PREVENTIVO. Ele preserva estado, mas não declara etapa concluída, salvo se houver declaração explícita no pacote de origem ou decisão humana registrada.

---

### 12.2. PACOTE_HANDOFF_VAQUITA

DEFINIÇÃO:
Pacote formal e obrigatório de preservação de estado para situações de prioridade máxima.

USAR QUANDO:

1. FIM_DE_CAPÍTULO = sim;
2. houver tentativa de mudança de capítulo;
3. houver risco crítico;
4. houver perda de estado confiável;
5. houver condição expressa de handoff obrigatório;
6. a Vaquita exigir PACOTE_HANDOFF_VAQUITA.

NÃO SIGNIFICA AUTOMATICAMENTE:

1. que o novo chat deve revisar novo parágrafo;
2. que PROXIMO está liberado;
3. que pendências BVAA foram resolvidas;
4. que retornos auxiliares pendentes foram integrados;
5. que a etapa está concluída, salvo declaração explícita.

FORMULAÇÃO OBRIGATÓRIA:
Este é um PACOTE_HANDOFF_VAQUITA. Ele preserva formalmente o estado em condição obrigatória. A etapa só deve ser tratada como concluída se isso estiver explicitamente declarado no pacote de origem ou em decisão humana registrada.

---

## 13. Trava contra conclusão indevida

TRAVA:
O Handoff não pode declarar etapa concluída apenas porque gerou pacote.

REGRA:
Gerar pacote é preservar estado.

Gerar pacote não é concluir etapa.

Gerar PACOTE_HANDOFF_PREVENTIVO não conclui etapa.

Gerar PACOTE_HANDOFF_VAQUITA só conclui etapa se a conclusão já estiver declarada no pacote de origem ou confirmada pelo usuário humano.

FORMULAÇÃO PADRÃO:
STATUS_DA_ETAPA:
não concluída / concluída explicitamente / a confirmar

MOTIVO:
[...]

REGRA DE SEGURANÇA:
Na dúvida, usar:

STATUS_DA_ETAPA:
a confirmar

MOTIVO:
o pacote preserva estado, mas não contém declaração suficiente para afirmar conclusão de etapa.
