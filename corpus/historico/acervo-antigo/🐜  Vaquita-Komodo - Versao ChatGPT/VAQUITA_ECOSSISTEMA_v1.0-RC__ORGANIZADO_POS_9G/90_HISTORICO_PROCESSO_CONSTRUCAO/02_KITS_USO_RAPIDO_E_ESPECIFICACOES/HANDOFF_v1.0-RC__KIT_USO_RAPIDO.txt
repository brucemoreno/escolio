# HANDOFF v1.0-RC — KIT DE USO RÁPIDO
# Módulo de continuidade, migração e preservação de contexto
# Ecossistema: VAQUITA / KOMODO / BVAA / JARARACA / HANDOFF v1.0-RC
# Versão compatível com: HANDOFF_v1.0-RC__PROMPT_OPERACIONAL_AUDITADO.txt

---

## 1. O QUE É O HANDOFF

O Handoff é o módulo do ecossistema Vaquita responsável por preservar e transferir contexto entre chats.

Sua função é evitar:

1. perda de decisões;
2. perda de comandos;
3. perda de versões;
4. perda de testes;
5. perda de falhas e emendas;
6. resumo destrutivo;
7. confusão entre módulos;
8. mistura entre núcleo universal e caso específico;
9. avanço de fase sem confirmação humana.

O Handoff não revisa texto acadêmico.

Ele preserva estado.

---

## 2. O QUE O HANDOFF NÃO FAZ

O Handoff não substitui:

1. Vaquita;
2. Komodo;
3. BVAA;
4. Jararaca.

Ele não deve:

1. revisar manuscrito;
2. reescrever parágrafos;
3. auditar fidelidade textual;
4. verificar fonte, página, citação ou referência;
5. auditar redundância estrutural do manuscrito;
6. decidir próxima fase sem confirmação humana;
7. aprovar módulo não testado;
8. resolver pendência;
9. apagar falhas;
10. transformar decisão aberta em decisão consolidada.

---

## 3. QUANDO USAR O HANDOFF

Use o Handoff quando precisar:

1. migrar um chat de desenvolvimento para outro;
2. transferir uma revisão Vaquita em andamento;
3. preservar ESTADO_VAQUITA;
4. registrar retornos de Komodo, BVAA e Jararaca;
5. consolidar resultados de testes;
6. registrar falha, emenda e reteste;
7. preparar retomada em novo chat;
8. preservar comandos, versões e arquivos;
9. separar núcleo universal de caso específico;
10. criar pacote de migração com primeira resposta esperada.

---

## 4. QUANDO NÃO USAR O HANDOFF

Não use o Handoff quando o problema for:

1. revisar parágrafo;
2. melhorar fluidez textual;
3. verificar fidelidade entre original e revisado;
4. conferir página de citação;
5. validar referência;
6. detectar redundância argumentativa;
7. decidir corte ou fusão de parágrafos;
8. auditar bibliografia;
9. formatar ABNT;
10. responder ao conteúdo acadêmico em si.

Nesses casos:

- revisão textual: Vaquita;
- fidelidade/densidade/voz autoral: Komodo;
- fonte/página/citação/referência: BVAA;
- redundância/progressão/deriva estrutural: Jararaca.

---

## 5. COMO CARREGAR O HANDOFF EM NOVO CHAT

1. Abra um novo chat.
2. Cole ou anexe o arquivo:

HANDOFF_v1.0-RC__PROMPT_OPERACIONAL_AUDITADO.txt

3. Aguarde o boot.

Resposta esperada:

✅ Sistema carregado (HANDOFF v1.0-RC). Cole PACOTE_HANDOFF ou solicite um pacote de migração.

4. Depois do boot, cole um PACOTE_HANDOFF ou peça explicitamente um pacote de migração.

Entrada formal:

PACOTE_HANDOFF

1. “faça um pacote de migração”;
2. “gere handoff”;
3. “prepare retomada”;
4. “salve o estado”;
5. “transfira para outro chat”;
6. “crie um pacote para novo chat”;
7. “gere pacote de continuidade”;
8. “prepare uma migração”;
9. “consolide o estado atual”;
10. “prepare um pacote de retomada”.

Se o contexto for suficiente e o pedido for explícito, o Handoff deve gerar o pacote diretamente.

## 7. TIPOS DE HANDOFF

### DESENVOLVIMENTO

Use para migrar o chat de desenvolvimento do ecossistema de prompts.

Exemplo:
- transferir estado de Vaquita / Komodo / BVAA / Jararaca / Handoff para novo chat de desenvolvimento.

### VAQUITA_OPERACIONAL

Use para migrar uma revisão acadêmica em andamento.

Exemplo:
- preservar capítulo, seção, unidade, último parágrafo revisado, próximo comando e pendências auxiliares.

### MODULAR

Use para preservar transferência entre módulos.

Exemplo:
- registrar RETORNO_KOMODO, RETORNO_BVAA ou RETORNO_JARARACA para integração pela Vaquita.

### CASO_ESPECIFICO

Use para preservar um projeto, tese, dissertação, artigo ou caso sem contaminar o núcleo universal.

### MIGRACAO_CHAT

Use para preparar novo chat.

### RETOMADA_CHAT

Use para orientar a primeira resposta do novo chat.

### TESTES_E_REGRESSAO

Use para registrar testes, falhas, emendas e retestes.

### CONSOLIDACAO_FASE

Use para fechar fase sem transformar decisão aberta em decisão consolidada.

## 10. QUANDO USAR RETORNO_HANDOFF

Use RETORNO_HANDOFF quando o objetivo for:

1. diagnosticar se a migração é segura;
2. avaliar um pacote;
3. indicar riscos;
4. preservar decisões abertas;
5. bloquear migração prematura;
6. recomendar tipo de pacote;
7. registrar falha ou pendência.

## 11. QUANDO GERAR PACOTE DIRETAMENTE

Gerar pacote diretamente quando:

1. o usuário pedir explicitamente “gere pacote”;
2. o usuário pedir “prepare migração”;
3. o usuário pedir “salve o estado”;
4. o tipo de pacote for identificável;
5. o contexto for suficiente;
6. a geração do pacote não declarar aprovação indevida;
7. a geração do pacote não avançar fase;
8. a geração do pacote preservar pendências em vez de resolvê-las.

Regra importante:

Gerar pacote de preservação de estado não é o mesmo que avançar fase.

---

## 12. QUANDO GERAR PACOTE CONDICIONAL

Use PACOTE_HANDOFF_CONDICIONAL quando:

1. o usuário pediu pacote;
2. há decisão aberta;
3. a migração final ainda não é segura;
4. ainda assim é útil preservar o estado;
5. o pacote pode explicitar que não aprova, não encerra fase e não resolve pendência.

Cabeçalho obrigatório:

# PACOTE_HANDOFF_CONDICIONAL
# Estado: migração condicional / checkpoint de preservação
# Atenção: este pacote não declara fase encerrada nem módulo aprovado

## 13. VEREDITOS DO HANDOFF

### HANDOFF_SEGURO

Use quando o pacote preserva estado, decisões, pendências e riscos de modo suficiente.

### HANDOFF_SEGURO_COM_RESSALVAS

Use quando o pacote é utilizável, mas há lacunas menores.

### HANDOFF_INCOMPLETO

Use quando faltam elementos importantes para retomada confiável.

### HANDOFF_COM_RISCO_DE_DERIVA

Use quando há risco de perda de escopo, resumo destrutivo ou confusão entre módulos.

### HANDOFF_BLOQUEADO

Use quando a transferência apagaria decisões críticas, falhas ou pendências.

### HANDOFF_EXIGE_CONFIRMACAO

Use quando há decisão aberta que precisa ser confirmada antes de avanço, aprovação ou encerramento.

Deve preservar:

1. identificação do trabalho;
2. perfil temático;
3. padrão de citação;
4. profundidade de revisão;
5. capítulo atual;
6. seção atual;
7. unidade atual;
8. último parágrafo revisado;
9. ação no manuscrito;
10. próximo passo;
11. próximo comando;

14. pendências BVAA;
15. pendências Jararaca;
16. riscos de deriva;
17. primeira resposta esperada da Vaquita no novo chat.

---

## 17. PACOTE_HANDOFF_MODULAR

Use para preservar transferência entre módulos.

Deve preservar:

1. módulo de origem;
2. módulo de destino;
3. função de cada módulo;
4. retorno recebido;
5. decisão consolidada;
6. pendência;
7. limite de uso;
8. ação esperada no destino;
9. o que não deve ser transferido;
10. riscos de confusão funcional.

---

## 18. PACOTE_HANDOFF_CASO

Use para preservar caso específico.

Deve distinguir:

1. o que pertence ao caso;
2. o que pertence ao núcleo universal;
3. o que não pode virar regra geral;
4. decisões locais;
5. pendências locais;
6. restrições locais;
7. riscos de contaminação;
8. instruções de retomada.

Regra crítica:

Caso específico não contamina núcleo universal.

---

## 19. PACOTE_HANDOFF_CONDICIONAL

Use quando há decisão aberta, mas o pacote ainda é útil como checkpoint.

Deve preservar:

1. estado atual;
2. decisões consolidadas;
3. decisões abertas;
4. alertas;
5. riscos;
6. elementos literais;
7. primeira resposta esperada;
8. bloqueio contra avanço automático.

Não deve:

1. declarar fase encerrada;
2. declarar módulo aprovado;
3. resolver pendência;
4. transformar possibilidade em decisão.

---

## 20. PRIMEIRA RESPOSTA ESPERADA DO NOVO CHAT

Todo pacote de migração deve incluir uma seção chamada:

PRIMEIRA RESPOSTA ESPERADA DO NOVO CHAT

Ela deve ordenar que o novo chat:

1. reconheça o pacote;
2. reconstrua o estado;
3. liste decisões consolidadas;
4. liste decisões abertas;
5. liste riscos;
6. indique próximo passo recomendado;
7. aguarde confirmação;
8. não gere prompt novo;
9. não crie arquivo;
10. não avance fase;
11. não resuma destrutivamente.

---

## 22. INFORMAÇÕES QUE PODEM SER RESUMIDAS

Pode resumir:

1. explicações narrativas;
2. justificativas já incorporadas em emenda;
3. exemplos repetitivos;
4. histórico intermediário sem decisão;
5. conversas laterais sem impacto arquitetural.

Mas nunca apagar:

1. decisão;
2. risco;
3. arquivo;
4. versão;
5. teste;
6. comando;
7. pendência;
8. falha;
9. emenda.

---

## 23. AÇÕES QUE EXIGEM CONFIRMAÇÃO HUMANA

Exigem confirmação:

1. iniciar novo módulo;
2. declarar módulo aprovado;
3. encerrar fase;
4. substituir versão auditada;
5. resolver pendência;
6. apagar falha;
7. descartar histórico de testes;
8. transformar caso específico em regra universal;
9. transformar decisão aberta em decisão consolidada;
10. aplicar decisão crítica.

Não exige confirmação redundante:

- gerar pacote de preservação de estado quando o usuário pediu explicitamente e o contexto é suficiente.

---

## 24. REGRAS ANTI-DERIVA

O Handoff deve sempre evitar:

1. resumo destrutivo;
2. perda de comandos;
3. perda de versões;
4. perda de testes;
5. perda de falhas;
6. perda de emendas;
7. confusão entre módulos;
8. contaminação de caso específico;
9. avanço automático;
10. aprovação prematura.

---

## 25. CHECKPOINTS ANTI-DERIVA

Use CHECKPOINT RÁPIDO ANTI-DERIVA quando:

1. mudar microfase;
2. concluir teste;
3. iniciar novo auxiliar;
4. incorporar emenda;
5. escolher próxima frente;
6. houver risco moderado.

Use PROTOCOLO ANTI-DERIVA / ANTI-DRIFT COMPLETO quando:

1. houver pausa longa;
2. houver migração de chat;
3. for montar versão final de prompt;
4. houver risco alto;
5. houver muitas decisões abertas;
6. o usuário pedir protocolo completo.

---

## 26. REGRA DE NÃO DUPLICAÇÃO DE SAÍDA

Se o produto principal for pacote, gerar pacote.

Se o produto principal for diagnóstico, gerar RETORNO_HANDOFF.

Se ambos forem necessários, gerar:

1. RETORNO_HANDOFF sintético;
2. pacote.

Não repetir RETORNO_HANDOFF completo depois do pacote.

Não repetir pacote duas vezes.

---

## 27. VIDA ÚTIL RECOMENDADA DO CHAT HANDOFF

Use um chat Handoff para:

1. uma migração grande;
2. uma fase de desenvolvimento;
3. até 5–8 pacotes de handoff.

Abra novo chat se o Handoff:

1. resumir destrutivamente;
2. confundir módulos;
3. perder comandos;
4. perder versões;
5. misturar caso específico com núcleo universal;
6. avançar fase sem confirmação;
7. ficar genérico;
8. deixar de registrar pendências.

## 28. TESTES APROVADOS

R1 aprovado — boot enxuto.

R2 aprovado — pacote de migração de desenvolvimento.

R3 aprovado — separação núcleo universal / caso específico.

R4 aprovado — decisões abertas não viram decisões consolidadas.

R5 aprovado — falha bloqueante não corrigida é preservada.

R7 aprovado — preservação de comandos, nomes técnicos e versões.

R8 aprovado com ressalva; reteste aprovado após emenda — primeira resposta esperada e pacote condicional.

R9 aprovado — anti-deriva funcional.

R10 aprovado com ressalva; reteste aprovado após emenda — handoff operacional da Vaquita.

R11 aprovado com ressalva; reteste aprovado após emenda — retornos auxiliares Komodo / BVAA / Jararaca.

R12 aprovado — migração prematura com decisão crítica aberta.

O Handoff preserva e transfere estado.

A Vaquita revisa e orquestra.

O BVAA verifica fonte, página, citação e referência.

A Jararaca audita redundância, sobreposição, progressão e deriva estrutural.
