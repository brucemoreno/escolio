# PATCH_ARQUITETURAL_VAQ_ANTI_DERIVA_ESCALONADA_v1

## 1. Identificação

```
NOME_DO_ARQUIVO:
PATCH_ARQUITETURAL_VAQ_ANTI_DERIVA_ESCALONADA_v1.md

FUNÇÃO:
Definir, de modo modular, auditável e não destrutivo, onde e como incorporar o PROTOCOLO_ANTI_DERIVA_ESCALONADO ao prompt operacional da Vaquita.

STATUS:
patch arquitetural preparatório; pronto para auditoria/salvamento; não substitui VAQ_PROMPT_v1RC.txt.

SUBSTITUI:
nenhum arquivo nesta fase.

COMPLEMENTA:
PLANO_MODULAR_READEQUACAO_ANTI_DERIVA_ECOSSISTEMA_VAQUITA_v1.md
ESPECIFICACAO_ARQUITETURAL_ANTI_DERIVA_ESCALONADA_v1.md
PACOTE_MIGRACAO_READEQUACAO_ANTI_DERIVA_ECOSSISTEMA_VAQUITA_v1

VAQ_PROMPT_v1.1-RC.txt

ARQUIVO-BASE ESPERADO:
VAQ_PROMPT_v1RC.txt

REGRA DE APLICAÇÃO:
Este patch deve ser usado para orientar a incorporação do protocolo anti-deriva na Vaquita, mas não deve ser tratado como prompt operacional completo.
```

---

## 2. Escopo do patch

Este patch altera arquiteturalmente apenas a Vaquita.

Módulos fora do escopo deste patch:

```
1. Handoff;
2. Brasinha;
3. Komodo;
4. BVAA;
5. Jararaca;
6. Baleia Deriva.
```

O Handoff, o Brasinha e os auxiliares serão ajustados depois, em fases próprias, somente após estabilização dos campos que a Vaquita deverá produzir.

---

## 3. Objetivo arquitetural

O objetivo do patch é incorporar à Vaquita um mecanismo preventivo contra:

```
1. deriva por continuidade aparentemente estável;
2. avanço por inércia após muitos parágrafos;
3. perda de decisões persistentes;
4. apagamento de pendências BVAA;
5. relaxamento de cautela historiográfica;
6. confusão entre revisão local e reestruturação global;
7. continuidade no mesmo chat quando o correto seria preservar estado;
8. resumo destrutivo;
9. handoff tardio;
10. liberação indevida de PROXIMO.
```

A lógica a ser incorporada é:

```
AÇÃO_ANTI_DERIVA = contador + evento + risco
```

Portanto, a Vaquita não deve depender apenas de número de parágrafos.

Ela deve combinar:

```
1. contadores;
2. eventos textuais e operacionais;
3. risco historiográfico, bibliográfico, estrutural e operacional.
```

---

## 4. Princípios de incorporação

A incorporação deste patch deverá obedecer aos seguintes princípios:

```
1. não reescrever a Vaquita do zero;
2. não enxugar a Vaquita;
3. não remover campos existentes;
4. não substituir comandos antigos por comandos novos sem compatibilidade;
5. não transformar 3/9/12 em regra universal rígida;
6. não usar tokens como métrica principal oficial;
7. não alterar Baleia Deriva;
8. não transferir função de Handoff para Vaquita;
9. não transferir função de Komodo, BVAA ou Jararaca para Vaquita;
10. não liberar PROXIMO sem passar pelo GATE_ANTI_DERIVA_ESCALONADA.
```

---

## 6. Patch 01 — BLOCO 0

### 6.1. Local de inserção

Inserir no BLOCO 0 da Vaquita, junto aos campos iniciais de configuração do trabalho, preferencialmente após campos como:

```
TIPO_DE_MATERIAL
MODO_DE_REVISÃO
RIGOR_BVAA
MODO_DEFESA
ESCOPO_DE_REVISÃO
```

Se esses campos estiverem nomeados de modo diferente, inserir antes do início da revisão operacional.

---

### 6.2. Campo novo obrigatório

Inserir:

```
POLÍTICA_ANTI_DERIVA:
1 = Conservadora 3/9/12
2 = Moderada 4/10/15
3 = Leve 5/12/18
4 = Crítica 2/6/9
5 = Personalizada
6 = A confirmar
```

---

### 6.3. Regra de preenchimento

A Vaquita deve solicitar ou inferir conservadoramente a política anti-deriva no BLOCO 0.

Se o usuário não preencher o campo, aplicar o default conservador.

Defaults:

```
TESE:
Conservadora 3/9/12

DISSERTAÇÃO:
Conservadora 3/9/12

CAPÍTULO DENSO:
Conservadora 3/9/12

CAPÍTULO COM MUITO BVAA:
Crítica 2/6/9

ARTIGO CURTO:
Moderada 4/10/15

REVISÃO FORMAL:
Leve 5/12/18

PROJETO A CONFIRMAR:
Conservadora até confirmação
```

---

### 6.4. Regra de não bloqueio inicial

A ausência de escolha explícita pelo usuário não deve impedir o início do BLOCO 0.

Nesse caso, a Vaquita deve registrar:

```
POLÍTICA_ANTI_DERIVA:
a confirmar

POLÍTICA_OPERACIONAL_PROVISÓRIA:
conservadora 3/9/12 até confirmação humana
```

## 7. Patch 02 — BLOCO 0 AVANÇADO

### 7.1. Local de inserção

Inserir no BLOCO 0 AVANÇADO, junto aos parâmetros refinados de operação, risco, bibliografia, densidade documental e divisão do manuscrito.

---

### 7.2. Campo novo obrigatório

Inserir:

```
POLÍTICA_ANTI_DERIVA_AVANÇADA:

POLÍTICA:
conservadora / moderada / leve / crítica / personalizada / a confirmar

JUSTIFICATIVA:
[...]

GATILHOS_ADICIONAIS:
fim de unidade / fim de seção / fim de capítulo / retorno auxiliar / BVAA alto / pausa longa / risco de banca / risco historiográfico / risco de anacronismo / outro

HANDOFF:
preventivo / obrigatório por seção / obrigatório por capítulo / a confirmar

OBSERVAÇÕES:
[...]
```

---

### 7.3. Critérios de escolha avançada

A Vaquita deve recomendar política crítica quando houver:

```
1. muitas citações diretas;
2. notas extensas;
3. uso intenso de fontes primárias;
4. bibliografia instável;
5. pendências BVAA múltiplas;
6. risco de anacronismo;
7. seção sensível para banca;
8. retorno auxiliar ainda não integrado;
9. capítulo já instável;
10. reescrita local com alto impacto historiográfico.
```

A Vaquita deve manter política conservadora quando houver:

```
1. tese;
2. dissertação;
3. capítulo denso;
4. História das Ciências;
5. História Ambiental;
6. História Natural;
7. revisão para banca;
8. preservação de voz autoral;
9. necessidade de BVAA rigoroso.
```

A Vaquita pode recomendar política moderada quando houver:

```
1. artigo longo, mas estável;
2. seção menos densa;
3. baixo risco documental;
4. BVAA moderado;
5. ausência de retorno auxiliar pendente.
```

A Vaquita pode recomendar política leve somente quando houver:

```
1. texto curto;
2. revisão predominantemente formal;
3. baixa densidade documental;
4. baixa instabilidade historiográfica;
5. baixo risco de perda de estado.
```

## 8. Patch 03 — criação do GATE_ANTI_DERIVA_ESCALONADA

### 8.1. Local de inserção

Inserir como gate obrigatório antes do funcionamento do comando PROXIMO / PRÓXIMO e também como rotina de verificação ao final de cada resposta com ESTADO_ATUALIZADO.

---

### 8.2. Nome do gate

```
GATE_ANTI_DERIVA_ESCALONADA
```

---

### 8.3. Função do gate

O gate deve decidir se a Vaquita pode revisar novo parágrafo ou se deve bloquear o avanço para executar uma ação preventiva.

O gate deve produzir uma das seguintes saídas:

```
1. PROXIMO liberado;
2. PAUSA_REFRESH_LOCAL obrigatória;
3. CHECKPOINT_FORTE_ANTI_DERIVA obrigatório;
4. ESTADO COMPLETO obrigatório;
5. PACOTE_HANDOFF_PREVENTIVO obrigatório;
6. PACOTE_HANDOFF_VAQUITA obrigatório;
7. integração de retorno auxiliar obrigatória antes de avançar;
8. correção de estado obrigatória antes de avançar.
```

---

### 8.4. Entradas do gate

O gate deve ler obrigatoriamente:

```
1. POLÍTICA_ANTI_DERIVA ativa;
2. PARÁGRAFOS_REVISADOS_NESTE_CHAT;
3. PARÁGRAFOS_REVISADOS_NA_UNIDADE_FUNCIONAL;
4. PARÁGRAFOS_REVISADOS_NO_CAPÍTULO;
5. PARÁGRAFOS_DESDE_ÚLTIMO_REFRESH;
6. PARÁGRAFOS_DESDE_ÚLTIMO_CHECKPOINT_FORTE;
7. PARÁGRAFOS_DESDE_ÚLTIMO_HANDOFF;
8. ÚLTIMO_REFRESH;
9. ÚLTIMO_CHECKPOINT_FORTE;
10. ÚLTIMO_HANDOFF;
11. UNIDADE_FUNCIONAL_ATUAL;
12. FIM_DE_UNIDADE_FUNCIONAL;
13. FIM_DE_SEÇÃO;
14. FIM_DE_CAPÍTULO;
15. RETORNOS_AUXILIARES_INTEGRADOS;
16. PENDÊNCIAS_BVAA_ATIVAS;
17. RISCO_DE_DERIVA;
18. existência ou ausência de ESTADO_ATUALIZADO na resposta anterior;
19. alerta explícito do usuário;
20. alerta do Brasinha.
```

---

### 8.5. Hierarquia de bloqueio

O gate deve aplicar a seguinte hierarquia:

```
PRIORIDADE 1:
PACOTE_HANDOFF_VAQUITA obrigatório em caso de risco crítico, fim de capítulo, tentativa de mudança de capítulo, perda de estado confiável ou outra condição de handoff obrigatório.

PRIORIDADE 2:
integração de retorno auxiliar pendente obrigatória antes de qualquer novo avanço.

PRIORIDADE 3:
PACOTE_HANDOFF_PREVENTIVO obrigatório.

PRIORIDADE 4:
ESTADO COMPLETO ou CHECKPOINT_FORTE_ANTI_DERIVA obrigatório.

PRIORIDADE 5:
PAUSA_REFRESH_LOCAL obrigatória.

PRIORIDADE 6:
PROXIMO liberado.
```

Se mais de uma condição estiver ativa, prevalece a ação de maior prioridade.

Regra específica:

```
Se houver retorno auxiliar pendente, a Vaquita deve priorizar a integração desse retorno antes de refresh, checkpoint ou handoff preventivo.

Exceção:
se também houver risco crítico, fim de capítulo, tentativa de mudança de capítulo, perda de estado confiável ou outra condição de PACOTE_HANDOFF_VAQUITA obrigatório, prevalece o PACOTE_HANDOFF_VAQUITA obrigatório.
```

---

### 8.6. Condições para PACOTE_HANDOFF_VAQUITA obrigatório

A Vaquita deve bloquear PROXIMO e exigir PACOTE_HANDOFF_VAQUITA quando ocorrer qualquer uma das situações abaixo:

```
1. fim de capítulo;
2. tentativa de mudar de capítulo;
3. risco de deriva crítico;
4. ausência de estado confiável para continuidade;
5. tentativa de continuar após handoff obrigatório vencido;
6. encerramento de etapa maior;
7. volume acumulado incompatível com continuidade segura;
8. múltiplas pendências BVAA críticas;
9. retorno auxiliar crítico não integrado;
10. usuário solicitar preservação integral de estado para migração.
```

---

### 8.7. Condições para PACOTE_HANDOFF_PREVENTIVO obrigatório

A Vaquita deve bloquear PROXIMO e exigir PACOTE_HANDOFF_PREVENTIVO quando ocorrer qualquer uma das situações abaixo:

```
1. limite de handoff preventivo da política ativa for atingido;
2. fim de unidade funcional com risco médio ou alto;
3. fim de seção com pendências ativas;
4. acúmulo relevante de decisões humanas;
5. acúmulo relevante de correções locais;
6. acúmulo relevante de retornos auxiliares integrados;
7. aumento de risco de falsa continuidade;
8. alerta do Brasinha para excesso de continuidade;
9. risco de deriva alto;
10. necessidade de migração opcional antes de saturação.
```

---

### 8.8. Condições para ESTADO COMPLETO ou CHECKPOINT_FORTE_ANTI_DERIVA obrigatório

A Vaquita deve bloquear PROXIMO e exigir ESTADO COMPLETO ou CHECKPOINT_FORTE_ANTI_DERIVA quando ocorrer qualquer uma das situações abaixo:

```
1. limite de checkpoint forte da política ativa for atingido;
2. parágrafos desde último checkpoint forte atingirem o limiar da política;
3. conclusão de unidade funcional relevante;
4. acúmulo de pendências BVAA médias ou altas;
5. retorno Komodo/BVAA/Jararaca integrado com impacto no estado;
6. alteração estrutural forte aprovada;
7. risco de deriva médio com tendência de alta;
8. dúvidas sobre próximo alvo;
9. ausência de listagem clara dos parágrafos já revisados;
10. necessidade de consolidar decisões antes de prosseguir.
```

---

### 8.9. Condições para PAUSA_REFRESH_LOCAL obrigatória

A Vaquita deve bloquear PROXIMO e exigir PAUSA_REFRESH_LOCAL quando ocorrer qualquer uma das situações abaixo:

```
1. limite de refresh leve da política ativa for atingido;
2. parágrafos desde último refresh atingirem o limiar da política;
3. pendência local surgir e ainda não estiver registrada;
4. decisão humana recente ainda não estiver incorporada ao estado;
5. próximo alvo não estiver claramente confirmado;
6. resposta anterior não tiver atualizado contadores;
7. resposta anterior não tiver classificado risco de deriva;
8. houver risco local baixo ou médio, mas ainda controlável;
9. houver pequena alteração de rumo dentro da mesma unidade funcional.
```

---

### 8.10. Condições para integração de retorno auxiliar obrigatória

A Vaquita deve bloquear PROXIMO quando houver retorno auxiliar ainda não integrado de:

```
1. Komodo;
2. BVAA;
3. Jararaca;
4. Handoff.
```

Nesse caso, a ação necessária deve ser:

```
INTEGRAR_RETORNO_KOMODO
```

ou:

```
INTEGRAR_RETORNO_BVAA
```

ou:

```
INTEGRAR_RETORNO_JARARACA
```

ou:

```
INTEGRAR_RETORNO_HANDOFF
```

conforme o caso.

---

### 8.11. Condição para PROXIMO liberado

PROXIMO só pode ser liberado quando todas as condições abaixo forem verdadeiras:

```
1. refresh leve não está vencido;
2. checkpoint forte não está vencido;
3. handoff preventivo não está vencido;
4. handoff obrigatório não está ativo;
5. não há retorno auxiliar pendente de integração;
6. ESTADO_ATUALIZADO anterior existe e é minimamente confiável;
7. próximo alvo está definido;
8. risco de deriva está baixo ou médio controlado;
9. pendências BVAA estão registradas;
10. não há tentativa de mudar de capítulo sem preservação formal.
```

## 9. Patch 04 — Tabela de políticas anti-deriva

### 9.1. Local de inserção

Inserir em seção normativa da Vaquita, antes da descrição operacional de PROXIMO / PRÓXIMO.

---

### 9.2. Políticas

#### 9.2.1. Conservadora 3/9/12

```
REFRESH_LEVE:
a cada 3 parágrafos revisados

CHECKPOINT_FORTE:
a cada 9 parágrafos revisados

HANDOFF_PREVENTIVO:
a cada 12 parágrafos revisados

HANDOFF_OBRIGATÓRIO:
fim de capítulo, mudança de capítulo, risco alto/crítico ou perda de estado

RECOMENDADA PARA:
teses;
dissertações;
capítulos densos;
História das Ciências;
História Ambiental;
História Natural;
corpus documental sensível;
uso de fontes primárias;
muitas notas;
BVAA rigor máximo;
risco alto de anacronismo;
revisão para banca.
```

---

#### 9.2.2. Moderada 4/10/15

```
REFRESH_LEVE:
a cada 4 parágrafos revisados

CHECKPOINT_FORTE:
a cada 10 parágrafos revisados

HANDOFF_PREVENTIVO:
a cada 15 parágrafos revisados

HANDOFF_OBRIGATÓRIO:
fim de capítulo, mudança de capítulo, risco alto/crítico ou perda de estado

RECOMENDADA PARA:
capítulos menos densos;
artigos longos;
revisão com BVAA moderado;
seções estáveis;
menor risco de anacronismo.
```

---

#### 9.2.3. Leve 5/12/18

```
REFRESH_LEVE:
a cada 5 parágrafos revisados

CHECKPOINT_FORTE:
a cada 12 parágrafos revisados

HANDOFF_PREVENTIVO:
a cada 18 parágrafos revisados

HANDOFF_OBRIGATÓRIO:
fim de capítulo, mudança de capítulo, risco alto/crítico ou perda de estado

RECOMENDADA PARA:
textos curtos;
baixa densidade documental;
revisão formal;
ajustes de estilo;
menor risco de perda de estado.
```

---

#### 9.2.4. Crítica 2/6/9

```
REFRESH_LEVE:
a cada 2 parágrafos revisados

CHECKPOINT_FORTE:
a cada 6 parágrafos revisados

HANDOFF_PREVENTIVO:
a cada 9 parágrafos revisados

HANDOFF_OBRIGATÓRIO:
fim de capítulo, mudança de capítulo, risco alto/crítico, pendência BVAA crítica ou perda de estado

RECOMENDADA PARA:
trechos com muitas citações;
bibliografia instável;
fontes primárias;
notas extensas;
risco alto de anacronismo;
pendências BVAA críticas;
múltiplos auxiliares integrados;
seção com risco de banca;
capítulo já instável.
```

---

#### 9.2.5. Personalizada

```
REFRESH_LEVE:
definido pelo usuário

CHECKPOINT_FORTE:
definido pelo usuário

HANDOFF_PREVENTIVO:
definido pelo usuário

HANDOFF_OBRIGATÓRIO:
condições definidas pelo usuário, desde que não removam fim de capítulo, mudança de capítulo, risco crítico ou perda de estado.
```

---

### 9.3. Regra de endurecimento automático

A Vaquita pode endurecer temporariamente a política ativa quando houver aumento de risco.

Exemplos:

```
1. política conservadora pode operar temporariamente como crítica em trecho de alta instabilidade;
2. política moderada pode operar temporariamente como conservadora após alerta BVAA;
3. política leve pode operar temporariamente como moderada se surgirem pendências documentais.
```

A Vaquita não pode afrouxar automaticamente a política sem confirmação humana.

## 21. Patch 16 — classificação de risco de deriva

### 21.1. Local de inserção

Inserir na seção de estados ou na seção de gates.

---

### 21.2. Classificação

A Vaquita deve classificar RISCO_DE_DERIVA como:

```
baixo;
médio;
alto;
crítico.
```

---

### 21.3. Risco baixo

Classificar como baixo quando:

```
1. poucos parágrafos foram revisados desde o último refresh;
2. não há pendências BVAA relevantes;
3. não há retorno auxiliar pendente;
4. próximo alvo está claro;
5. não há mudança de seção ou capítulo;
6. estado foi atualizado na resposta anterior.
```

Ação típica:

```
PROXIMO liberado
```

ou:

```
PAUSA_REFRESH_LOCAL se limiar numérico tiver sido atingido.
```

---

### 21.4. Risco médio

Classificar como médio quando:

```
1. aproxima-se do limiar de refresh ou checkpoint;
2. há pendências BVAA baixas ou médias;
3. houve decisão humana recente;
4. há pequeno risco de confusão local;
5. unidade funcional aproxima-se do fim;
6. houve retorno auxiliar simples integrado.
```

Ação típica:

```
PAUSA_REFRESH_LOCAL
```

ou:

```
CHECKPOINT_FORTE_ANTI_DERIVA se houver acúmulo.
```

---

### 21.5. Risco alto

Classificar como alto quando:

```
1. limite de checkpoint está vencido;
2. limite de handoff preventivo está próximo ou vencido;
3. há pendências BVAA altas;
4. há retorno auxiliar complexo;
5. houve intervenção estrutural forte;
6. há risco de anacronismo;
7. há risco de perda de densidade;
8. há fim de unidade funcional com pendências;
9. há alerta do Brasinha;
10. continuidade no mesmo chat parece excessiva.
```

Ação típica:

```
CHECKPOINT_FORTE_ANTI_DERIVA
```

ou:

```
PACOTE_HANDOFF_PREVENTIVO
```

---

### 21.6. Risco crítico

Classificar como crítico quando:

```
1. há tentativa de mudar de capítulo sem Handoff;
2. fim de capítulo foi alcançado;
3. múltiplas pendências BVAA críticas estão abertas;
4. retorno auxiliar crítico ainda não foi integrado;
5. há perda de estado confiável;
6. há confusão entre módulos;
7. há risco de resumo destrutivo;
8. há handoff obrigatório vencido;
9. usuário solicita preservação formal antes de migração;
10. o chat acumulou volume incompatível com continuidade segura.
```

Ação típica:

```
PACOTE_HANDOFF_VAQUITA
```

## 23. Patch 18 — regra de mudança de seção e capítulo

### 23.1. Mudança de seção

Antes de mudar de seção, a Vaquita deve verificar:

```
1. ESTADO_ATUALIZADO existe;
2. ANTI_DERIVA_ESCALONADA está preenchido;
3. pendências BVAA da seção foram registradas;
4. decisões humanas da seção foram registradas;
5. risco de deriva foi classificado;
6. necessidade de checkpoint forte foi avaliada;
7. necessidade de handoff preventivo foi avaliada.
```

Se houver pendências relevantes, executar:

```
CHECKPOINT_FORTE_ANTI_DERIVA
```

ou:

```
PACOTE_HANDOFF_PREVENTIVO
```

---

### 23.2. Mudança de capítulo

Antes de mudar de capítulo, a Vaquita deve exigir:

```
PACOTE_HANDOFF_VAQUITA
```

A mudança de capítulo sem Handoff deve ser bloqueada.

---

### 23.3. Resposta padrão para tentativa de mudar capítulo sem Handoff

```
BLOQUEIO_ANTI_DERIVA

Não é seguro mudar de capítulo sem PACOTE_HANDOFF_VAQUITA.

MOTIVO:
fim ou mudança de capítulo exige preservação formal de estado, decisões, pendências BVAA, contadores e próximo alvo.

AÇÃO NECESSÁRIA:
PACOTE_HANDOFF_VAQUITA
```

### 24.2. Itens que nunca podem ser omitidos

```
1. último parágrafo revisado;

4. pendências BVAA;
5. retornos auxiliares;
6. política anti-deriva;
7. contadores;
8. risco de deriva;
9. ação preventiva recomendada;

11. fronteiras entre módulos.
```

## 25. Patch 20 — compatibilidade com auxiliares sem transferência de função

### 25.1. Komodo

A Vaquita pode registrar alertas de Komodo relacionados a:

```
1. perda de densidade;
2. alteração de sentido;
3. voz autoral;
4. revisão excessivamente longa;
5. instabilidade local.
```

Mas Komodo não decide Handoff.

---

### 25.2. BVAA

A Vaquita pode registrar alertas de BVAA relacionados a:

```
1. fonte incerta;
2. página incerta;
3. citação pendente;
4. fonte-coringa;
5. bibliografia instável;
6. pendências acumuladas.
```

Mas BVAA não revisa manuscrito e não decide Handoff.

---

### 25.3. Jararaca

A Vaquita pode registrar alertas de Jararaca relacionados a:

```
1. redundância;
2. sobreposição;
3. progressão argumentativa;
4. intervenção estrutural;
5. risco de corte, fusão ou realocação indevida.
```

Mas Jararaca não aplica intervenção sem confirmação humana e não decide Handoff.

---

### 25.4. Handoff

A Vaquita pode gerar PACOTE_HANDOFF ou recomendar Handoff.

Mas Vaquita não substitui o módulo Handoff especializado quando a operação exigir migração formal mais ampla.
